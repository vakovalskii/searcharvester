# Интерфейс исследования: чаты, картинки, визуализация

Статус: проект, до кода. Ветка `feat/neuraldeep-provider`. Ревью: `codex exec`,
раунды записаны в конце.

## Зачем

Сейчас интерфейс (`frontend/`) это форма, статус, лента событий лида и отчёт. Замечание
владельца по живому интерфейсу: мало интерактива, нет чатов сбоку, сабагентов не видно,
половина ленты служебные строки. Картинок нет ни во входе, ни в отчёте. Документ
описывает, что строим, на каких данных, в каком порядке и как проверяем.

## Факты из кода, на которые опирается план

- События (`simple_tavily_adapter/events.py`): `spawn`, `thought`, `message`,
  `tool_call`, `tool_result`, `plan`, `commands`, `note`, `done`; поля `ts`, `job_id`,
  `agent_id`, `parent_id`, `type`, `payload`. Поток `GET /research/{id}/events` (SSE),
  снимок `GET /research/{id}/snapshot`, на диске `jobs/<id>/events.jsonl`. Номера
  события нет: при переподключении SSE отдаёт историю заново, а `App.tsx` дописывает её
  в конец (дубли).
- По ACP в реальном времени идут события только лида. Для сабагентов `events.py` сам
  синтезирует `spawn`, `message`, `done` из вызова и результата `delegate_task` с
  идентификатором `_sub_agent_id(delegate_call_id, номер_задачи)`, а оркестратор
  досыпает их из `HERMES_HOME/sessions/session_*.json` (`_backfill_subagents`).
- Hermes v0.21 файлы сессий не пишет (`/opt/data/sessions` пуст). Сессии живут в
  `HERMES_HOME/state.db`: `sessions(id, parent_session_id, started_at, ended_at,
  end_reason, tool_call_count, input_tokens, output_tokens, model, cwd, ...)`,
  `messages(id, session_id, role, content, tool_calls, tool_name, tool_call_id,
  timestamp, token_count, finish_reason, ...)`. Сессия лида равна ACP-сессии
  (`sessionProvenance.acpSessionId == currentHermesSessionId`).
- Сторож (`guard.py`) шлёт `note kind: guard` только на предупреждении, остановке и
  дописывании; лимиты в поток не попадают; итог в `done.payload.guard` есть не на всех
  путях завершения (нет на `_fail`, таймауте, отмене).
- `/extract` отдаёт `id, url, title, content, pages`; `_extract_markdown_for_url`
  возвращает только `(title, markdown)`, HTML, путь каскада и `final_url` теряются;
  кеш `_extract_cache` хранит то же самое. `extract.py` всегда сначала зовёт
  `/extract`, сохраняет `extracts/<id>.md` без описи.
- Состояние заданий только в памяти (`Orchestrator._jobs`): после перезапуска
  адаптера `/research/{id}`, `/snapshot`, `/events` отвечают 404, хотя на диске всё есть.
  Событие `spawn` лида не содержит `depth`; задание, отменённое в очереди, `spawn`
  не пишет вовсе.
- `App.tsx` держит одно общее состояние (`events`, отчёт, статус); асинхронные ответы
  не привязаны к заданию.
- Markdown рендерят два места: `ReportView.tsx` и `LogTimeline.tsx` (сводки
  сабагентов), оба через `react-markdown` с настройками по умолчанию.
- API без аутентификации, слушает `127.0.0.1`, CORS разрешает `localhost:9762`.
  CORS не защищает от «простых» запросов: обычная HTML-форма с любого сайта,
  открытого в браузере, может отправить POST на `localhost:8010`.
- Модель лида `qwen3.6-35b-a3b-noreason` понимает картинки (замер и чекпоинт).

## Этап 0. Защита существующего API

До любого нового эндпоинта, потому что задание запускает агента с шеллом.

- Все изменяющие запросы (`POST`, `DELETE`) требуют заголовок
  `X-Searcharvester-Client: 1`. Нестандартный заголовок заставляет браузер делать
  preflight, и чужой origin отсекается CORS; простая форма его поставить не может.
  Плюс проверка `Origin`, если он есть: только из `CORS_ORIGINS`. Заголовок в том
  же этапе начинают слать все вызовы: `frontend/src/lib/api.ts` (создание, отмена,
  всё новое), скрипты навыков, `bench/`.
- Проверка `Host` на каждом запросе, включая GET и SSE: только имена из
  `ALLOWED_HOSTS` (по умолчанию `localhost`, `127.0.0.1`, `tavily-adapter`, с
  портом и без), иначе 400. Это закрывает DNS rebinding: чужой домен, указывающий на
  127.0.0.1, для браузера свой origin, и CORS его не останавливает, а читать список
  заданий, отчёты и поток он смог бы.
- Любой идентификатор задания, откуда бы он ни пришёл (путь, `?job=` у `/media`,
  `parent_job` в теле; у канала агента задание берётся из его токена), проверяется одной функцией
  `job_id(id)`: шаблон `^[0-9a-f]{16}$` и существование задания. Путь на диске из
  него строит только адаптер и только в своём `STATE_DIR/<id>/` (агент туда писать
  не может, см. ниже), а пути в рабочей папке агента передаются `runner` как
  относительные имена из фиксированного списка (`report.md`, `plan.md`,
  `extracts/<extract_id>.md`, `input/<n>.png`), без `..` и без абсолютных путей.
- **Агенты в отдельном контейнере.** Сейчас адаптер и все агенты работают в одном
  контейнере под одним пользователем: агент из шелла пишет всё, что может адаптер,
  шлёт сигналы его процессу и читает окружение соседнего задания. Изоляция по uid
  внутри одного контейнера потянула бы возможности ядра, настройки Docker, гонки с
  симлинками и повторное использование uid, поэтому граница проводится контейнером:
  - сервис `runner` (новый, тот же образ Hermes): небольшой демон, который запускает
    `hermes acp` по команде адаптера и отдаёт ему stdin, stdout и stderr процесса
    через одно соединение на задание (TCP во внутренней сети compose, наружу порт не
    публикуется). Демон и агенты работают под одним непривилегированным
    пользователем, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`;
  - адаптер не монтирует рабочие папки агентов и не открывает ни одного файла,
    который агент может менять. Всё файловое делает `runner` по запросу адаптера:
    создание папки задания, чтение `report.md` и извлечений, запись унаследованных
    извлечений и загруженных картинок, удаление; каждый путь открывается
    относительно дескриптора папки задания с `O_NOFOLLOW` по каждой компоненте,
    открытый дескриптор проверяется на обычный файл. Гонок со сменой симлинка у
    адаптера нет, потому что у адаптера нет доступа к этой файловой системе;
  - всё, что пишет адаптер, лежит у него: `STATE_DIR/<id>/` (отдельный том
    `./state:/srv/searxng-docker/state` в compose, entrypoint выставляет владельца и
    0700): `job.json`, `events.jsonl`, `hermes.log` (stderr приходит по соединению),
    журнал выдачи `served.jsonl`, `final_report.md` запасного пути, кеш `/media`;
  - у каждого задания свой `HERMES_HOME` внутри `runner` (`/srv/hermes-jobs/<id>`):
    `config.yaml` и навыки копируются туда из образа только на чтение, `state.db`,
    логи и кеш свои; хвост сабагентов (A2) получает строки своей базы через тот же
    `runner`, чужие задания в ней не появляются;
  - при отмене, таймауте и конце задания `runner` убивает группу процессов задания,
    затем все процессы, у которых в окружении токен этого задания, и только после
    этого удаляет его `HERMES_HOME`;
  - `runner` не живёт без адаптера: соединение задания оборвалось (адаптер упал или
    перезапущен), значит через 10 секунд без переподключения задание убивается той же
    уборкой; кроме того у каждого задания собственный дедлайн в `runner`
    (`RESEARCH_TIMEOUT_SEC` плюс 60 секунд, передаётся при запуске), который
    срабатывает даже при живом соединении. При старте адаптер просит `runner`
    убить всё, что тот ещё держит, и только потом помечает незавершённые задания
    `interrupted`;
  - остаточный риск, записанный явно: задания внутри `runner` друг от друга не
    изолированы (один пользователь), процесс одного задания, переживший уборку или
    запущенный параллельно, может читать файлы и окружение другого. Все задания
    принадлежат одному владельцу инстанса, адаптер, его состояние и токен
    интерфейса при этом недоступны. Полная изоляция (контейнер на задание) в
    разделе «Потом».
- **Два канала доступа к API вместо одного.**
  - Канал агента: оркестратор на каждое задание выдаёт случайный токен (32 байта) в
    окружение Hermes (`SEARCHARVESTER_JOB_TOKEN`), скрипты шлют его заголовком
    `Authorization: Bearer`. Задание определяется по токену, заголовок
    `X-Searcharvester-Job` больше ничего не решает. С этим токеном доступны только
    `/search`, `/extract`, `/extract/{id}/{page}` (страницы только своих
    извлечений), `/extract/local`; всё остальное 403. Токен гаснет вместе с
    заданием.
  - Канал интерфейса: токен интерфейса (`SEARCHARVESTER_UI_TOKEN`, из окружения или
    случайный при старте) нужен для списка заданий, статуса, снимка, потока,
    `/media`, создания, отмены, `steer`, `queue`. Адаптер печатает в свой лог ссылку
    `http://localhost:9762/#token=...`, интерфейс забирает токен из фрагмента в
    `sessionStorage` и шлёт заголовком (SSE через `?token=`, потому что
    `EventSource` не умеет заголовки). Агенты токена не видят: его нет в их
    окружении, а процесс и логи адаптера в другом контейнере.
  - `X-Searcharvester-Client` и проверка `Origin` остаются как защита от
    простых форм, проверка `Host` против DNS rebinding тоже.
- Тесты изоляции (поддельный агент запускается через настоящий `runner` в compose):
  у процесса агента `CapEff`, `CapPrm`, `CapAmb` нулевые и `NoNewPrivs: 1`; из агента не
  виден ни один процесс адаптера (другое пространство PID) и нет пути к `STATE_DIR`;
  `report.md`, подменённый симлинком на системный файл, и папка, подменённая
  симлинком во время чтения, дают отказ `runner`, а не чужой файл; отмена и таймаут
  убирают все процессы задания, включая отцепившийся через `setsid` потомок; токен
  задания A не открывает `/extract/local` и страницы извлечений задания B и не даёт
  доступа к `/research*`; без токена интерфейса список, статус, поток и `/media`
  отвечают 401; после пересоздания контейнеров `STATE_DIR` на месте и задания
  открываются; перезапуск одного адаптера во время живого задания: процессы задания
  в `runner` исчезают не позже чем через 15 секунд, задание `interrupted`; задание,
  чей адаптер держит соединение, но пропустил таймаут, убивается дедлайном `runner`.
- Тесты: POST без заголовка 403; `Origin: https://evil.example` 403; форма
  `application/x-www-form-urlencoded` и `text/plain` без заголовка 403; `Host:
  evil.example` на GET 400; `job_id` с `../` и неверной длиной 422 во всех четырёх
  местах; папка задания-симлинк на другое задание 404; создание и отмена задания из
  интерфейса работают (vitest на `api.ts` проверяет заголовок у каждого изменяющего
  вызова).

## Этап A. Порядок в данных

### A1. Номер события и продолжение потока

`Event` получает `seq` (растёт с 1 в пределах задания, пишется в `events.jsonl`). SSE
отдаёт `id: <seq>`, сервер принимает `Last-Event-ID` и `?after=<seq>` и шлёт только
новое. Клиент хранит события в словаре по `seq`, дубль игнорирует. В старых
`events.jsonl` поля нет: при чтении с диска строке без `seq` присваивается её номер в
файле (с 1), это детерминированно и совпадает между снимком и потоком. Тесты: поток,
оборванный на середине и продолженный, даёт ровно тот же список, что и снимок; то же
для старого файла без `seq`.

### A2. Одна личность у сабагента

Канонический `agent_id` сабагента остаётся прежним: `_sub_agent_id(delegate_call_id,
номер_задачи)`. Два источника событий сводятся к нему:

- синтетика из `delegate_task` (`events.py`) даёт `spawn` с целью и, если база
  недоступна, итоговые `message` и `done`;
- хвост `state.db` (новый `subagents.py`) даёт шаги: `tool_call`, `tool_result`,
  `message`, `usage`, `done`. Сессия сабагента сопоставляется с задачей так же, как
  сейчас сопоставляется файл: по цели задачи в первом сообщении роли user
  (подстрока, как в `_goal_for_task_index`) и, при равенстве, по порядку
  `started_at` внутри одного вызова `delegate_task`; сессии чужого лида
  (`parent_session_id` не наш) игнорируются.
- Оркестратор ведёт карту покрытия `задача -> сессия базы или нет`. Итог задачи
  выпускает тот источник, который её покрывает: покрытая задача получает `done` из
  базы (когда у сессии есть `ended_at`), непокрытая получает `done` из результата
  `delegate_task`, как сейчас. Второй `done` по одной задаче не пишется.
- Сессия без пары получает временный id `sub-db-<8 символов id>`. На каждом тике
  несопоставленные сессии заново сверяются с непокрытыми задачами; нашлась пара,
  значит в поток уходит `note kind: alias {from, to}`, задача становится покрытой,
  а `reduce` склеивает события временного id с каноническим. Не нашлась до конца
  задания, значит остаётся отдельным агентом с пометкой «без задачи».
- База пропала посреди задания: покрытие замораживается, непокрытые задачи и
  задачи, чья сессия не успела закончиться, получают `done` из результата
  `delegate_task`; база вернулась, хвост продолжает с курсоров.
- Перед любым завершением задания оркестратор сверяет все задачи, у которых был
  `spawn`: задача без `done` (результат обрезан, в нём нет её записи, база
  недоступна, задание отменено или остановлено сторожем) получает
  `done {status: unknown, reason}`. Незакрытых агентов в конце не бывает.
- Чтение базы: `file:...?mode=ro`, `uri=True`, `timeout=0.5`, раз в 2 секунды, курсор
  по `messages.id` на каждую сессию; `database is locked` и отсутствие колонок дают
  пропуск тика или выключение хвоста с предупреждением, задание идёт дальше.
- Старые `_backfill_subagents` и `_index_sub_sessions` уходят, их место занимает
  финальный проход того же хвоста после конца хода.

Тесты: фикстура sqlite со схемой; смешанный поток (синтетика плюс база) даёт одного
агента на задачу и один `done`; курсор не теряет и не дублирует строки между тиками;
чужой лид игнорируется; сессия, сопоставленная не сразу, склеивается через `alias`;
несопоставленная до конца видна отдельно, а её задача закрыта результатом
`delegate_task`; база пропала и вернулась посреди задания, у каждой задачи ровно один
`done`; обрезанный результат пачки из трёх задач при недоступной базе даёт два
`done` из результата и один `unknown`; база без колонки не роняет задание.

### A3. Счётчики и лимиты в потоке

- В `spawn` лида кладутся `depth`, `parent_job` и `limits` (все поля `guard.Limits`).
- Раз в 5 секунд, если что-то изменилось, оркестратор пишет `note kind: usage` со
  всеми счётчиками сторожа; хвост базы пишет `usage` агента (его `input_tokens`,
  `output_tokens`, `tool_call_count`), в том числе для сессии лида (она тоже в
  `state.db`).
- Каждый путь завершения (`_finalize_success`, `_fail`, таймаут, отмена) пишет в
  `done` итоговые счётчики и лимиты. Тест проходит по всем четырём путям.

### A4. Задания на диске

- При создании задания пишется `STATE_DIR/<id>/job.json` (вне досягаемости агента,
  этап 0): `id, query, depth, parent_job,
  created_at, status: queued`; при получении слота `started_at, status: running`; на
  каждом пути завершения `status, finished_at, duration_sec, error, report_file`.
  Запись атомарная (временный файл и `os.replace`).
- Итоговый текст задания всегда лежит файлом: если агент написал `report.md`, это
  он (адаптер забирает его через `runner` и кладёт копию в `STATE_DIR`); если сработал
  запасной путь (ответ чатом с источниками) или провал с частичным текстом,
  оркестратор пишет его в `STATE_DIR/<id>/final_report.md`; `report_file` в `job.json`
  указывает, какой из двух отдавать.
- Прерванные перезапуском: при старте адаптер проходит `job.json` со статусом
  `queued` или `running`, ставит новый терминальный статус `interrupted`, дописывает в
  `events.jsonl` `done {status: interrupted}`, так что и снимок, и SSE такого задания
  завершаются.
- `GET /research/{id}`, `/snapshot`, `/events` сначала смотрят память, потом диск
  (`STATE_DIR/<id>/job.json`, `events.jsonl`, текст из `report_file`). `events.jsonl`
  тоже переезжает в `STATE_DIR`, чтобы агент не мог дописать себе событий. Задание со старого прогона без
  `job.json` читается из `events.jsonl`: запрос из `spawn` лида, статус только из
  `done` с `agent_id: "lead"` (итоги сабагентов не в счёт), `depth: "unknown"`; нет
  `done` лида, значит `interrupted`; нет даже `spawn` лида, значит 404.
- Новый `GET /research?limit=50&before=<created_at>`: список из памяти и с диска,
  новые сверху.
- Тесты: задание завершилось обычным путём, запасным путём и провалом, адаптер
  пересоздан, статус, снимок и текст те же; перезапуск во время `queued` и во время
  `running` даёт `interrupted` и закрытый SSE; старый файл, где последний `done`
  принадлежит сабагенту, а у лида `done` нет, читается как `interrupted`.

### A5. Что знает `/extract`

- `_extract_markdown_for_url` возвращает структуру `Extracted(title, content,
  final_url, path, images)` вместо пары; кеш хранит её целиком.
- `images`: до 3 штук `{src, alt, caption}`, только абсолютные http(s), без `data:`,
  иконок и картинок меньше 200×100 по атрибутам, только с быстрого пути (есть HTML);
  у ридера и браузера `images: []`.
- Ответ `/extract` получает `final_url`, `path`, `images`.
- Для запроса с токеном задания адаптер ведёт серверный журнал выдачи
  `STATE_DIR/<id>/served.jsonl`: `url, final_url, title, path, chars, images, sha256`
  каждого отданного текста. Он и только он источник правды для повторных и
  унаследованных чтений и для `/media` (картинка разрешена, если её `src` есть в
  `images` какой-то записи журнала этого задания; отдельного списка разрешений нет).
- `sha256` и `total_chars` считаются по полному тексту извлечения (все страницы, UTF-8)
  и отдаются в первом ответе `/extract` при любом `size`. Запросы страниц
  `/extract/{id}/{page}` тоже идут с токеном задания и токеном запроса. `extract.py`
  собирает страницы, сверяет хеш собранного файла и только при совпадении пишет
  запись в опись с `complete: true`; не совпало или страница не пришла, значит файл
  сохранён с `complete: false`, агенту это видно, повторно он не используется. Опись `extracts/manifest.jsonl` пишет агент в
  своей папке, поэтому ей адаптер не верит, она только подсказка скрипту.
- `extract.py` печатает `images` в своём выводе (агент видит их и может вставить) и
  пишет опись `extracts/manifest.jsonl`: `{url, final_url, id, file, title, path,
  images, sha256}` на каждое сохранение.

### A6. Кто что прочитал

Адаптер не знает агента, а окно времени называет читателем и того, кто страницу не
открыл. Поэтому связь через токен запроса:

- `search.py` и `extract.py` на каждый вызов генерируют случайный токен (16 hex),
  шлют его заголовком `X-Searcharvester-Request` и печатают первой строкой вывода
  `request_token: <токен>`; вывод инструмента целиком попадает в `tool_result` того
  агента, который вызвал (у лида из ACP, у сабагентов из `state.db`);
- каждое обращение к `/extract` и `/search` с токеном задания даёт событие `read`
  или `search` с этим токеном и всем, что нужно карточке: `url, final_url, title,
  path (fast|reader|browser|inherited), chars, images, extract_id, verdict`
  (для поиска `query, results[{url,title,domain}], verdict`), включая дубли и
  отказы сторожа; дедупликация только в карточках;
- `reduce` связывает `read` с агентом, в чьём `tool_result` встретился токен. Пока
  результата нет (сабагент ещё не записан в базу), читатель «ждёт»; когда результат
  пришёл позже, связь появляется сама, потому что состояние пересчитывается из
  событий. Токен так и не встретился, значит читатель «неизвестен», и карточка так и
  пишет, без догадок;
- у карточки источника список читателей хранится отдельно от самой карточки.

Тесты: два сабагента одновременно читают один URL, второй из кеша: оба записаны
читателями, событий `read` два, карточка одна; вызов `extract.py`, упавший до
запроса, читателем не становится; результат сабагента, пришедший из базы на 10
секунд позже события `read`, связывается; `read` без токена в выводе остаётся
«неизвестен».

## Этап B. Интерфейс: раскладка и чаты

- Три колонки, на узком экране вкладки. Слева список заданий (запрос, режим,
  статус, длительность, время), из `GET /research`. В центре схема агентов, под ней
  вкладки «Отчёт» и «Источники». Справа чаты агентов.
- Выбор глубины в форме: `quick` по умолчанию, `deep` с подписью про время и цену.
- Чат агента собирается из событий его `agent_id`: цель первым сообщением, мысли
  свёрнуты, вызов инструмента одной плашкой (поиск с запросом, чтение с доменом,
  запись с файлом), по клику аргументы и результат, в конце ответ. Служебное
  (`UsageUpdate`, `commands`, `permission`, `SessionInfoUpdate`, `usage`) скрыто
  переключателем.
- Состояние задания привязано к его id: все данные лежат в `Map<jobId, JobState>`,
  у каждого задания свой `AbortController` и своя подписка SSE; ответ, пришедший
  для задания, которое уже не открыто, попадает в его запись, а не на экран;
  переключение закрывает подписку прежнего.
- Всё состояние экрана считается чистой функцией `reduce(events)`: схема, чаты,
  карточки, счётчики. На ней же стоит перемотка (этап E).
- Клики связывают всё: узел схемы открывает чат агента, плашка чтения подсвечивает
  карточку, ссылка в отчёте подсвечивает карточку и прокручивает чат к месту чтения.
- Фронту нужны тесты: `vitest` для `reduce` (снимок задания в фикстуре даёт
  ожидаемое дерево агентов и карточек) и для переключения заданий (ответ старого
  задания, пришедший после переключения, не меняет экран).

## Этап C. Схема агентов и источники

- Узлы: лид в центре, сабагенты по кругу в порядке `spawn`, роль по тексту цели
  (исследователь, критик, проверка фактов). Состояние по последнему событию: думает,
  ищет, читает, пишет, готов, остановлен сторожем, ошибка. Анимация короткая,
  выключается при `prefers-reduced-motion`.
- У узлов лида и сабагентов нет колец: подтверждённого счётчика ходов, который
  совпадал бы с `max_turns` и `delegation.max_iterations`, в данных нет. На узле
  подпись с числом вызовов инструментов и токенами из `usage`. Полосы с лимитами есть
  только у задания целиком (вызовы LLM, входные токены, поиски, чтения из
  `note kind: usage` против `limits`), их считает сторож, лимиты у них настоящие. Срабатывание сторожа: узел
  краснеет, причина в подсказке, полоса с отметкой лимита.
- Нити от узла к карточкам, которые он читал (читатели из A6); источник, чей URL есть
  в `report.md`, выделен.
- SVG в React без графовой библиотеки: узлов не больше 6.
- Карточка источника: домен, заголовок, путь каскада, размер текста, читатели.
  Превью картинки появляется только в этапе D, до него карточки без превью.

## Этап D. Картинки: одна политика для всего markdown

> Сделано 30.09.26, но с источником разрешений от поиска, а не от `/extract`
> (A5 ещё нет). Журнал `STATE_DIR/<id>/media.jsonl` пишет `/search` с категориями
> `images` и `videos` для запросов с токеном задания: картинка, её превью, ролик и
> его превью. `/media` пускает только адреса из этого журнала (`media.py`), остальное
> по плану ниже. В интерфейсе `SafeMarkdown` и вкладка Media. Когда появится
> `served.jsonl`, его `images` добавятся в тот же список разрешений.

- Общий компонент `SafeMarkdown` для отчёта, сводок сабагентов в чатах и любого
  текста агента: `skipHtml`, ссылки только http(s) с `rel="noopener noreferrer"`,
  картинка рендерится только если её `src` есть в разрешениях задания и тогда
  через `/media`, иначе вместо неё ссылка-текст. `ReportView` и `LogTimeline`
  переводятся на него, прямых `ReactMarkdown` в коде не остаётся (проверка в тесте
  по исходникам).
- `GET /media?job=<id>&src=<url>`:
  - 404, если `src` нет в `images` ни одной записи журнала выдачи этого задания;
  - та же защита от SSRF, что у ридера (`is_safe_url`, закреплённый IP, ручные
    редиректы с проверкой каждого шага), запрос без `Referer` и cookies;
  - только `image/png|jpeg|webp|gif|avif` по сигнатуре первых байтов, SVG и всё
    остальное 415; больше 5 МБ 413; таймаут 10 с;
  - кеш в `STATE_DIR/<id>/media/<sha256(src)>.<ext>`, имя строит сервер, путь
    проверяется на вложенность;
  - ответ: `Cache-Control: private, max-age=86400`, `X-Content-Type-Options: nosniff`,
    `Content-Security-Policy: default-src 'none'`, `Content-Disposition: inline`.
- В навыке правило: картинка в отчёт только из `images` прочитанного источника,
  строкой `![подпись](src)` и ссылкой на страницу рядом.
- Тесты: чужой `src` 404, внутренний адрес 400, SVG 415, HTML под видом картинки 415,
  6 МБ 413, редирект на внутренний адрес 400, повторный запрос из кеша без сети.

## Этап F. Интерактив

### F1. Подсказка по ходу и очередь

Два разных действия с разными критериями:

- **Живая подсказка** `POST /research/{id}/steer {text}` (до 2000 символов,
  заголовок этапа 0) отправляет в идущую сессию `/steer <text>`. Hermes объявляет
  команду `steer`; как он обрабатывает prompt, пришедший во время хода, проверяется
  первым шагом этапа на поддельном агенте и на настоящем Hermes. Если Hermes так не
  умеет, живой подсказки нет и кнопки в интерфейсе нет.
- **Очередь** `POST /research/{id}/queue {text}`: текст ждёт конца хода. Принимается
  не больше 3 элементов на задание и не больше 2000 символов каждый; сверх этого,
  после начала финализации, в `queued` и на завершённом задании ответ 409. Каждый
  принятый элемент получает id. `_run` после возврата хода и до финализации
  отправляет элементы по одному новым ходом той же сессии, сторож считает их как
  обычно. Каждый принятый элемент заканчивается ровно одним событием
  `note kind: queued_result {id, status: done|dropped_budget|dropped_cancel|dropped_error}`.
- Оба действия пишутся в поток `note kind: steer|queued` с текстом.
- Тесты на поддельном агенте: элемент очереди, поставленный во время хода, даёт второй
  ход до `done`; четвёртый элемент 409; элемент после начала финализации 409; сторож
  остановил задание, оставшиеся элементы получают `dropped_budget`; отмена даёт
  `dropped_cancel`; у каждого принятого элемента ровно один `queued_result`; живая
  подсказка (если есть) приходит агенту в пределах текущего хода.

### F2. Продолжение после ответа

- Новое задание с `parent_job`. Лид получает вопрос, отчёт родителя и опись его
  источников.
- Копирование из родителя делает `runner` по команде адаптера: файлы извлечений,
  перечисленные в журнале выдачи родителя, с проверкой `sha256`, и опись для скрипта, собранная адаптером из того же
  журнала; каждый путь проверяется на вложенность в папку родителя, симлинки и
  не-обычные файлы пропускаются.
- `extract.py` перед сетью смотрит опись в текущей папке: совпал `url` или
  `final_url`, файл на месте и `sha256` сходится, значит отдаёт локальный файл и
  страницу не качает. Вместо `/extract` он зовёт `POST /extract/local {url, sha256}` с
  токеном задания и токеном запроса. Адаптер ищет запись с этим URL и хешем в
  журнале выдачи этого задания (повторное чтение в обычном задании, `path: local`),
  затем в журнале родителя (родитель берётся из `job.json` ребёнка, не из запроса,
  `path: inherited`). Нашёл: пишет событие `read` с метаданными из журнала, а для
  унаследованной записи ещё копирует её в журнал ребёнка, чем и выдаёт разрешения на
  картинки. Не нашёл: 404, и скрипт идёт обычным путём через `/extract`. Сети на
  найденной записи нет.
- Тест: продолжение с тремя источниками родителя, кеш адаптера очищен: обращений в
  сеть по этим URL ноль, событий `read` с `inherited` три, их картинки через
  `/media` ребёнка отдаются; URL, которого нет ни в одном журнале, на `/extract/local`
  404, и скрипт читает его по сети; повторное чтение в задании без родителя даёт
  `read` с `local`; источник, впервые прочитанный ребёнком, при повторе тоже `local`;
  подделанная агентом опись (чужой URL, неверный хеш) ничего не регистрирует;
  извлечение на 3 страницы переиспользуется только после сверки хеша целого файла;
  обрыв на второй странице даёт `complete: false` и повторное чтение по сети.

## Риски

- Схема `state.db` принадлежит Hermes. Хвост читает только нужные колонки и при их
  отсутствии выключается с предупреждением; тест на это есть (A2).
- Сопоставление сессии с задачей по тексту цели может ошибиться, если лид даст двум
  задачам одинаковую цель; тогда решает порядок `started_at`, а несопоставленное
  видно отдельным агентом.
- Связь «кто прочитал» по окну времени при одновременных чтениях одного URL даёт
  несколько читателей; это честно показано, а не угадано.
- `og:image` на чужом CDN может резать запросы без `Referer`; тогда превью нет.
- Картинки во входе растят промпт лида; лимит входных токенов quick может
  потребовать поправки.
